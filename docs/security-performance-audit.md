# Аудит безопасности и производительности — 2026-10-29

## Границы проверки

Проверены текущие Laravel API, проверки доступа workspace, CSRF/лимиты/сессии,
обработка ответов Fetch, React workspace, известные уязвимости npm/Composer.
Это анализ исходников и локальные регрессионные тесты, не pentest production.
Конфигурация Caddy/PHP-FPM, production `.env`, журналы и планы запросов production
не проверялись. Данные production и сохранённые legacy PHP-файлы не изменялись.

## Рефакторинг и производительность

- В `frontend/js/api.js` один внутренний `request()` формирует credentials,
  JSON и CSRF для существующих методов. Публичные URL/payload не изменены.
  Проверены все JSON-записи, ошибки и отсутствие автоматических повторов мутаций.
- Задачи группируются по `list_id` за один проход и мемоизируются по массиву задач.
  Прежняя схема сканировала весь массив для каждой карточки и её копий в просмотре.
  Подготовка данных изменилась с `O(число списков × число задач)` на
  `O(число задач + число списков)`, с дополнительными массивами ссылок `O(число задач)`.
- Устаревшие поисковые Fetch-запросы отменяются через `AbortController`.
  Проверка номера запроса сохраняется: отмена Fetch не гарантирует остановку уже
  запущенного SQL на сервере.
- `ResizeObserver` полноэкранной карточки больше не пересоздаётся на каждом
  рендере. Клавиатурное переключение использует актуальные списки, а не старое
  замыкание обработчика.

Локальный синтетический замер: 300 списков, 10 000 задач, 100 повторений после
прогрева. `filter` для каждой карточки — 2580 мс, группировка с lookup — 28 мс.
Это замер подготовки данных в Node.js, а не FPS браузера, SQL или время ответа
production. Времена зависят от машины и нагрузки; тесты проверяют линейное число
обращений к задачам, а не нестабильный порог миллисекунд.

## Остающиеся риски и следующие этапы

### 1. Подтверждение смены e-mail — высокий приоритет

`ProfileController` позволяет заменить основной e-mail без подтверждения нового
адреса. `AuthController::acceptCorporateInvitation()` связывает приглашение с
пользователем по совпавшему e-mail, не по текущей подтверждённой личности.
Это опасное сочетание для адресов, ещё не занятых зарегистрированным пользователем:
владение полем профиля не доказывает владение почтовым ящиком. Сам токен приглашения
остаётся длинным, хешируется, имеет срок действия и блокируется при принятии;
утечка/подбор токена здесь не подтверждены.

Нужен отдельный согласованный сценарий: подтверждённый основной адрес, проверка
личности при принятии приглашения, обработка существующих аккаунтов и старых
приглашений. Это затрагивает схему/формы и контракт авторизации; скрытно менять
его в рефакторинге нельзя. Не считать текущую реализацию полной проверкой владения
e-mail. Отдельно согласовать отзыв остальных сессий после восстановления пароля:
текущая архитектура не обеспечивает такой отзыв.

### 2. Конкурентные записи общих досок — средний приоритет

Блокировка строки текущего пользователя сериализует его собственные запросы,
но не запросы разных участников. Board lock используется не во всех действиях.
Возможны гонки назначения `sort_order`, очистки флагов и изменения/удаления списков.
Нужны согласованный порядок общих блокировок и многопроцессные тесты PostgreSQL.
Существующие однопроцессные тесты не доказывают отсутствие этих гонок.

### 3. Неограниченный объём workspace и поиска — средний приоритет

GET возвращает все списки/задачи; поиск по `POSITION(LOWER(...))` требует прохода
по тексту, обычный B-tree его не ускорит. Перестановка выполняет UPDATE для каждой
строки. Нужны замеры на реалистичном объёме, `EXPLAIN (ANALYZE, BUFFERS)` на
обезличенной копии и затем решение о пакетных UPDATE, индексах и пагинации.
Пагинация изменит API и UI; новые индексы требуют отдельной миграции. В этом этапе
они не добавлялись. Виртуализация/перерисовки всех React-карточек также не измерены
браузерным профилировщиком.

### 4. Production-конфигурация — обязательная отдельная проверка

- Все `/api/*` должны попадать в `public/index.php`; физические `public/api/*.php`
  нельзя выполнять напрямую. `server.php` защищает только локальную разработку.
- Проверить HTTPS, `APP_ENV=production`, `APP_DEBUG=false`, secure/HttpOnly cookies,
  файловый общий cache, права файлов, запрет доступа к dotfiles и непубличным
  каталогам. В `local` используется фиксированный тестовый код регистрации;
  это окружение нельзя публиковать.
- Проверить резервные копии и восстановление, лимиты Caddy, ресурсы PHP-FPM,
  маршрутизацию PHP и необходимость CSP/прочих security headers.
- Точечный `composer audit`/`npm audit` не обнаруживает все возможные ошибки
  приложения. После обновлений повторять аудит и тесты.

  `composer install --no-dev --optimize-autoloader` по обновлённому lock-файлу,
  новая локальная frontend-сборка и стандартный ручной выпуск приложения.
- На старте `ListDeleteDialog.jsx` и `workspace-ui.test.mjs` были вне Git.
  Их нужно включить в будущий коммит вместе с кодом, который их импортирует;
  иначе отдельный checkout не воспроизведёт текущую сборку/тесты.

Коммит, push, deployment, очистка production cache и изменение production-БД
в рамках проверки не выполнялись. Браузерные артефакты Safari и мобильная вёрстка
автоматически не проверялись.
