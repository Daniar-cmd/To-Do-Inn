# Полиглотная архитектура: Laravel + ASP.NET Core

## Целевая модель

Фронтенд и адреса страниц остаются на React/Vite. Laravel сохраняет регистрацию, вход, восстановление пароля, профиль и источник истины для пользовательской сессии. ASP.NET Core на .NET 10 LTS получает предметную область рабочего пространства: доски, списки, заметки, задачи, флаги, порядок карточек, повторение задач и поиск.

Оба backend работают с одной PostgreSQL и существующими таблицами. Схема, идентификаторы, ограничения, связи владения и формат данных сохраняются. Сервисы получают разные ограниченные DB-роли; миграции схемы контролируются отдельно. Не создавать дублирующие таблицы или копии данных без отдельной причины.

### Граница сессии и доверия

Laravel остаётся владельцем cookie, сессии и CSRF-токена. ASP.NET Core не читает Laravel session storage и не создаёт вторую пользовательскую сессию. Запросы рабочего пространства сначала проходят Laravel-проверку текущей сессии и CSRF, после чего Laravel передаёт запрос внутреннему ASP.NET Core с `user_id` и нужными атрибутами через защищённый локальный канал. Прямой внешний доступ к внутренним маршрутам ASP.NET Core закрыт.

Для производственного запуска определить аутентификацию межсервисного канала: предпочтительно localhost/private socket плюс подписанный короткоживущий assertion с `user_id`, `audience`, `issued_at`, `expires_at` и защитой от повторного использования. Секрет хранится вне Git. ASP.NET Core доверяет только этому assertion и повторно проверяет принадлежность запрошенного объекта пользователю/организации. Он не принимает `user_id` из тела браузерного запроса. Laravel остаётся публичным API gateway и проверяет CSRF до передачи изменяющего запроса.

Такой переход сохраняет текущие API-контракты `/api/workspace.php`, `/api/auth.php`, `/api/profile.php`, cookie и повторный вход не требуется. Новый ASP.NET Core код сначала работает за Laravel facade; после стабилизации Caddy может перенаправлять workspace маршрут на ASP.NET Core только если там реализованы проверка сессии/CSRF gateway-контракт, единые логи и откат.

## Три ступени миграции

Ступени идут от наиболее сложной и дающей наибольший выигрыш от строгих типов предметной области к более широкому охвату. Каждая ступень сохраняет публичный контракт и может быть отдельно откатана.

### 1. Задачи и их правила — максимальный выигрыш от C#

Первыми перенести обработку `create_task`, `update_task`, `toggle_task`, `move_task`, `reorder_task`, `stop_task_repeat` и удаление задачи, включая цепочки повторений. Это наиболее насыщенный правилами участок: ограниченные поля и enum срочности, дата/дедлайн/время, принадлежность задаче и списку, межсписочное перемещение, порядок, блокировки, сериализация изменений и связанные экземпляры повторения.

C# задаёт явные типы DTO, enum повторения, nullable поля, доменные проверки и транзакционные границы. Laravel продолжает проверять сессию/CSRF, валидирует входной HTTP-контракт и проксирует допустимую операцию в ASP.NET Core. На этой ступени остальные операции workspace по-прежнему обслуживает Laravel.

Готовность: сравнение прежнего и нового ответов на одинаковых сценариях; тесты на каждое действие, чужие/несуществующие ID, гонки порядка и повторений, откат транзакции; нет записи в базу в обход проверок владения; frontend не требует изменений.

### 2. Списки, доски, заметки и флаги

Перенести CRUD досок/списков/заметок, закрепление, общий порядок списков и заметок, флаги, загрузку/удаление изображений заметок и проверки ролей корпоративных досок. Сначала оставить Laravel gateway и совместимый JSON, затем постепенно переключить эти операции.

Сохранить транзакции под блокировкой пользователя/доски, правила последней доски, очистку неиспользуемых флагов, лимиты и MIME/размер изображений, права владельца организации. Изображения и заметки остаются в прежней PostgreSQL-схеме.

Готовность: тесты владельца и участника, междосочного доступа, pin/reorder, конкурентных обновлений, загрузок и удаления изображения; побайтовые данные аватаров/заметок и ID сохранены; откат на Laravel проверен на отдельном локальном окружении.

### 3. Чтение workspace, поиск и переключение маршрута

Перенести сборку полного workspace-ответа, список досок, поиск по буквальной подстроке и сериализацию JSON. Проверить, что ASP.NET Core возвращает прежнюю форму данных, сортировку, временные метки и все задачи подходящих списков. После этого workspace API может целиком обслуживаться ASP.NET Core, но Laravel остаётся владельцем auth/profile и gateway для идентификации/CSRF.

Затем подготовить production-маршрутизацию Caddy, systemd service, Kestrel на loopback, health/readiness, ограниченный DB-role, HTTPS, мониторинг и быстрый возврат workspace маршрута на Laravel. Не удалять Laravel WorkspaceController или legacy endpoints до отдельного периода наблюдения и подтверждённого отката.

Готовность: полный регрессионный набор API и frontend, нагрузочные проверки чтения/поиска, проверка логов и ошибок, репетиция deploy/rollback и сохранение production backup по действующей процедуре.

## Организация кода без лишних слоёв

Для сервиса используется `backend/Workspace.Api/`. Первую операцию реализовать прямым Npgsql-запросом с параметрами и транзакцией; это соответствует малому объёму перенесённого кода. При расширении предметной области отдельно оценить EF Core, не добавляя его заранее. Не вводить общие repository/service слои без конкретной необходимости и не менять PHP Composer или npm зависимости ради .NET.

Миграциями PostgreSQL управляет один выбранный владелец схемы. На переходный период существующие Laravel миграции остаются источником схемы; EF Core не запускает автоматическое создание/изменение таблиц при старте. ASP.NET Core читает/пишет существующие таблицы через явное сопоставление имен, типов, timestamp, identity и nullable-колонок. Каждое последующее изменение схемы обсуждается один раз и отражается в выбранном источнике миграций.

## Локальная и production схема

- Laravel: `127.0.0.1:8001`; остаётся публичным входом Vite для auth/profile и временным gateway к workspace.
- ASP.NET Core: отдельный loopback порт, например `127.0.0.1:8002`; Vite/Caddy напрямую к нему не ходит на ранних этапах.
- PostgreSQL: та же локальная development database только после backup; тесты используют отдельную изолированную БД и отдельную роль.
- Production: Caddy → Laravel/PHP-FPM; Laravel → внутренний ASP.NET Core сервис. Прямой доступ к Kestrel из интернета закрыт.
- Конфигурация .NET хранится в отдельном локальном env-файле/secret store, исключённом из Git; в репозитории только безопасный example без ключей.

## Текущий выбор .NET

Для нового сервиса принять .NET 10 LTS. Перед установкой на VPS проверить доступность поддерживаемого runtime/SDK для целевой Debian 13 и выбрать self-contained или framework-dependent публикацию; Node/Vite на VPS не нужны. SDK на Mac и runtime на VPS должны поддерживать выбранную версию.

## Подготовленное локальное окружение

В экспериментальной ветке создан `backend/Workspace.Api/` на .NET 10 с `/health` и защищённым `/internal/handshake` и запуском на `127.0.0.1:8002`. Локально установлен SDK 10.0.404. Создана отдельная `todo_inn_aspnet_test`: в неё скопирована только схема 10 таблиц из `todo_inn_laravel_test`, без строк данных. Создана роль `todo_inn_aspnet_test` с DML-доступом только к таблицам рабочего пространства и чтением пользователей/организаций; подключение хранится в игнорируемом `.env.aspnet.testing` с правами файла 0600. Миграции и профиль этой роли недоступны. Текущий Laravel и Vite не направляют запросы в ASP.NET Core.

## Реализованный внутренний handshake

Laravel-класс `app/Support/WorkspaceBridge.php` формирует HMAC-SHA256 assertion для `GET /internal/handshake`. Подписываются метод, путь, `user_id`, Unix timestamp, случайный nonce и SHA-256 тела. ASP.NET Core принимает его только с loopback, проверяет 32-байтный секрет, окно ±30 секунд, подпись постоянным по времени сравнением и отклоняет повтор nonce. Секрет совпадает в игнорируемых `.env.laravel` и `.env.aspnet.local`; публичные `.env.example` и `.env.aspnet.example` содержат только пустые поля.

Перенесены все семь действий с задачами: `create_task`, `toggle_task`, `update_task`, `move_task`, `reorder_task`, `delete_task` и `stop_task_repeat`. `WorkspaceController` после Laravel auth/CSRF держит транзакцию и блокировку строки пользователя и подписывает вызов внутреннего .NET endpoint. В ветках моста используется PostgreSQL `FOR NO KEY UPDATE`: он сериализует записи пользователя и допускает `KEY SHARE`, необходимый .NET при вставке задачи по внешнему ключу. Для удаления и остановки повторений Laravel после проверки доступа дополнительно блокирует строку владельца корпоративной доски. .NET повторно проверяет доступ к списку/задаче, пишет в прежние таблицы PostgreSQL и возвращает прежний JSON. Создание поддерживает описание, важность, срочность, дату или дедлайн, локацию и время, существующий или новый флаг и начальную запись серии повторений. Для создания и изменения порядка advisory lock по ID списка сериализует операции от разных участников корпоративной доски; перенос между списками берёт блокировки в порядке ID.

Для .NET добавлен Npgsql 10.0.3 и отдельная локальная DB-роль с чтением пользователей/досок/списков, ограниченным изменением задач и вставкой задач/флагов. Семь флагов `WORKSPACE_BRIDGE_*_TASK` и `WORKSPACE_BRIDGE_STOP_TASK_REPEAT` по умолчанию выключены и оставляют запросы в PHP; при ошибке включённого bridge Laravel возвращает 503 без повторной записи. На отдельной тестовой БД проверены поля и JSON новой задачи, флаги, повторение, границы доступа и валидации, 12 конкурентных созданий, перестановки и переносы, а также запреты удаления, остановка всех экземпляров серии и сохранение флагов, используемых заметкой или списком.

Фоновое расписание Laravel `tasks:repeat` остаётся на 00:05 UTC. При `WORKSPACE_BRIDGE_REPEAT_TASKS=true` команда по-прежнему перечисляет активные серии и блокирует владельца через `FOR NO KEY UPDATE`, но расчёт следующей даты и вставку до 366 экземпляров за проход выполняет .NET через подписанный `POST /internal/tasks/repeat`. .NET берёт advisory lock списка, повторно читает последнюю активную задачу и не создаёт дубли при повторном или параллельном запуске. Команда возвращает ошибку при сбое моста без PHP fallback. На изолированной базе проверены конец месяца, високосный год, повторный и параллельный запуск, предел 366 и полный локальный путь Laravel CLI → .NET. Никакой production-планировщик этим шагом не менялся.

Полный локальный контрактный прогон выполнен на отдельной `todo_inn_aspnet_test`: запросы шли через настоящий Laravel HTTP API с cookie-сессией, обновлённым после входа CSRF-токеном и всеми включёнными bridge-флагами. Проверены создание, переименование, завершение, перестановка, перенос, удаление и остановка повторений с последующим чтением workspace. Отдельно одновременно запускались генератор и `stop_task_repeat`, `move_task`, `delete_task`; активное повторение после остановки не сохранялось, последовательности не дублировались, а порядок задач в списках оставался непрерывным. Временный пользователь и связанные данные удалены после прогона. Обычные локальные флаги всё ещё выключены.

Для локального запуска используйте переменные из `.env.aspnet.local` и `dotnet run --project backend/Workspace.Api --no-launch-profile`; URL должен оставаться `http://127.0.0.1:8002`. Тестовая строка подключения хранится отдельно в `.env.aspnet.testing`; не направляйте её на development или production базу. При нескольких экземплярах ASP.NET Core nonce-cache нужно вынести в общий store или заменить протокол; текущий вариант рассчитан на один локальный процесс.

## С чего начать

Следующий шаг — включить все bridge-флаги в игнорируемом локальном `.env.laravel`, запустить обычные Vite/Laravel/.NET процессы на `todo_inn_laravel_dev` и провести браузерную проверку рабочего пространства. После локального периода проверки подготовить один сфокусированный коммит экспериментальной ветки. Production остаётся на Laravel до отдельного согласованного этапа.
