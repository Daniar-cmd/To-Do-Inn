# Полный переход бэкенда To Do Inn с PHP на C#

Локальный Docker и production работают на ASP.NET Core. PHP-исходники доступны в истории Git, а предыдущий серверный релиз сохранён для отката. Этапы ниже описывают историю перехода и результаты проверок.

## Целевое состояние

Весь бэкенд To Do Inn переходит на C# и ASP.NET Core (.NET 10 LTS). ASP.NET Core обслуживает API, cookie-сессии, CSRF, регистрацию, вход, восстановление пароля, профили, организации, рабочее пространство, фоновые задачи, почту, загрузку файлов и эксплуатационные команды. Фронтенд остаётся на React и TypeScript с Vite, Gulp и SCSS. Caddy отдаёт собранный `dist/` и проксирует `/api/*` в ASP.NET Core.

Существующие URL страниц и API, формы JSON, HTTP-статусы, идентификаторы, хеши паролей, данные PostgreSQL и поведение интерфейса сохраняются. ASP.NET Core обрабатывает маршруты с суффиксом `.php` как обычные HTTP-маршруты. После перехода для сборки и запуска бэкенда нужен .NET, для сборки фронтенда по-прежнему нужен Node.js.

PostgreSQL остаётся единственным хранилищем. Существующие таблицы и данные принимаются без копирования в параллельную модель. Миграции схемы переходят к одному .NET-механизму после сверки текущей Laravel-истории. Автоматическое изменение production-схемы при старте приложения запрещено.

Рабочий объём ограничен заменой PHP-бэкенда и настройкой маршрутов к новому API. Компоненты, стили, анимации, тексты, каталог дизайна и сборка фронтенда остаются на текущем стеке. Смена API, продуктовых правил, структуры базы или инфраструктуры требует отдельного решения. Перед переносом сверить поведение исходной ветки с выпускаемой версией, включая паузу регистрации из `master` и ограничения профиля.

## Итоговая структура

```text
frontend/                  Действующий React/TypeScript frontend и SCSS
backend/                   ASP.NET Core API, сессии, фоновые задачи и команды
tests/
  js/                      Действующие тесты фронтенда
  ToDoInn.Api.Tests/       Интеграционные тесты .NET API
```

Это целевая схема каталогов. Текущие PHP-файлы служат эталоном поведения и точкой отката до проверенного переключения. На переходном этапе схемой PostgreSQL управляют существующие Laravel-миграции.

## Единая граница безопасности

ASP.NET Core становится единственным публичным приложением и владельцем аутентификации. Оно выдаёт защищённую cookie с `HttpOnly`, `Secure` и подходящим `SameSite`, хранит серверную сессию, проверяет CSRF для изменяющих запросов и определяет пользователя только из подтверждённой сессии. Клиентские `user_id`, `account_id` и права доступа не считаются доверенными.

Вход проверяет существующие Argon2id и bcrypt-хеши без сброса паролей и массового перехеширования. Смена пароля отзывает все активные сессии пользователя. При переключении на новый формат сессии планируется один повторный вход. Состояние регистрации сохраняется по настройкам выпуска.

Проверки владения досками, организациями, списками, заметками, задачами и флагами выполняются сервером внутри транзакции. ASP.NET Core использует параметризованные Npgsql-команды или явно настроенный EF Core. Секреты, строки подключения, почтовые ключи и ключи Data Protection хранятся вне Git.

## Три ступени перехода

Каждая ступень завершается совместимым работающим приложением, проверкой на отдельной PostgreSQL-базе и зафиксированной точкой отката. Production переключается только после отдельного решения о выпуске.

### 1. Предметная область и данные

Перенести весь workspace в ASP.NET Core. Сюда входят чтение рабочего пространства, поиск, доски, списки, заметки, изображения заметок, задачи, флаги, закрепление, общий порядок карточек, переносы, повторение задач, корпоративные права и фоновые задания.

Уже реализованы семь операций задач: `create_task`, `toggle_task`, `update_task`, `move_task`, `reorder_task`, `delete_task`, `stop_task_repeat`, а также генерация повторяющихся экземпляров. Текущий HMAC bridge через Laravel является временным переходным механизмом. Следующая работа на этой ступени начинается с браузерной проверки реализованных действий, затем переносит чтение workspace и оставшиеся операции объектов.

Критерии завершения:

- ASP.NET Core воспроизводит все текущие ответы `/api/workspace.php` и правила доступа;
- конкурентные создание, перенос, изменение порядка, удаление и повторение сохраняют целостный порядок;
- файлы и BYTEA данные проходят прежние ограничения размера и MIME;
- фоновые повторы выполняются .NET hosted service или отдельной .NET-командой;
- Laravel временно проверяет сессию и CSRF для публичных запросов и передаёт операции workspace в .NET через внутренний мост.

### 2. Весь backend и эксплуатационные команды

Перенести регистрацию, подтверждение почты, вход, выход, восстановление пароля, профиль, аватары, организации, приглашения, уведомления, сессии, CSRF, лимиты запросов, почтовую отправку, health/readiness и диагностику. Сохранить `/api/auth.php`, `/api/profile.php`, `/api/workspace.php` и `/api/notes/{noteId}/image`, включая бинарный ответ при чтении изображения.

На этой ступени готовится передача управления схемой PostgreSQL. Текущая схема принимается baseline-миграцией без повторного создания таблиц и без изменения пользовательских данных. После передачи новые миграции создаются только в .NET. Интеграционные тесты .NET используют изолированную `todo_inn_aspnet_test` и откатывают свои записи или очищают только собственные тестовые данные.

Критерии завершения:

- существующий React-клиент работает с cookie и CSRF-токеном ASP.NET Core. При переключении пользователь заново входит в аккаунт;
- все текущие auth/profile/workspace контракты проходят интеграционные тесты через настоящий HTTP host;
- старые bcrypt и Argon2id пользователи входят без сброса пароля;
- смена пароля отзывает все сессии;
- почта, rate limits, фоновые команды и загрузки проверены на сбой и повторный запуск;
- локальный запуск бэкенда и его диагностика выполняются через .NET.

### 3. Переключение бэкенда на ASP.NET Core

Переключить локальный Vite proxy, затем маршруты Caddy на ASP.NET Core. Caddy продолжает отдавать страницы и ассеты из `dist/`, а API направляет в Kestrel на loopback. Проверить доступность всех прежних страниц и `/favicon.svg`.

Критерии завершения:

- действующий React-клиент проходит браузерную проверку входа, профиля, работы с досками и списками, перетаскивания задач, поиска и загрузки изображений;
- бэкенд проверяется через `dotnet test` и публикуется через `dotnet publish`, фронтенд собирается прежней командой `npm run build`;
- Caddy, systemd, health checks, Data Protection keys, логи и backup/rollback проверены на репетиции;
- после периода наблюдения PHP-FPM и мост Laravel → .NET выводятся из эксплуатации. Удаление старых PHP-файлов выполняется отдельно после проверки отката.

## Текущий прогресс экспериментальной ветки

В `backend/Workspace.Api/` создан .NET 10 сервис на loopback `127.0.0.1:8002`. Он использует Npgsql 10.0.3, HMAC-SHA256 assertion от Laravel и отдельную ограниченную роль PostgreSQL. Реализованы семь действий с задачами и генератор повторяющихся задач. Проверены поля и JSON, флаги, даты, повторение, границы доступа, конкурентные создания, перестановки, переносы, остановка серии и удаление.

Контрактный прогон семи операций и генератора выполнен на отдельной `todo_inn_aspnet_test` через Laravel HTTP API с cookie-сессией и CSRF. Мост сохраняется до переключения публичного API на ASP.NET Core с собственной аутентификацией. Для запуска существующего сервиса используется `dotnet run --project backend/Workspace.Api --no-launch-profile` с окружением из `.env.aspnet.local`.

## Перенос остальных операций workspace

Чтение доски и буквальный поиск перенесены в ASP.NET Core за выключенным по умолчанию флагом `WORKSPACE_BRIDGE_READ_WORKSPACE`. Laravel принимает прежний GET и передаёт параметры в теле подписанного внутреннего POST. Для включения тестовой роли нужны права SELECT на таблицы workspace, организации и членство, включая `notes`. Маршрут чтения не требует миграции схемы. Выключение флага возвращает чтение в Laravel.

На заполненной изолированной `todo_inn_aspnet_test` сопоставлены JSON и статусы Laravel-контроллера с результатами SQL нового маршрута в девяти сценариях. Сравнение охватило состав и порядок карточек, корпоративный доступ, буквальный поиск, пустую выдачу и недоступные доски. Тестовые записи откатили.

Создание отдельного флага перенесено за выключенным по умолчанию `WORKSPACE_BRIDGE_CREATE_FLAG`. SQL проверен на личной и корпоративной досках, чужой доске, корпоративном доступе без членства и конфликте дубликатов. Дальше нужен прогон по подписанному HTTP-мосту через действующий React-клиент и перенос оставшихся операций досок, списков и заметок.

Создание и редактирование досок работают через выключенный по умолчанию `WORKSPACE_BRIDGE_SAVE_BOARD`. Первая запись списка и запись новой доски создаются одной командой PostgreSQL. На изолированной базе проверены личная и корпоративная доски, ограничения owner, недоступная доска, запрет смены корпоративного типа и дубликат имени. Записи откатили. Перед включением нужно проверить разрешения роли .NET на INSERT и UPDATE для досок, INSERT для списка и соответствующие последовательности.

Удаление досок и списков перенесено за выключенным по умолчанию `WORKSPACE_BRIDGE_DELETE_WORKSPACE_ITEM`. Laravel принимает прежний DELETE и проверяет сессию, CSRF и параметры. .NET повторно проверяет доступ и выполняет удаление в транзакции. На изолированной базе проверены запрет удаления последней доски, выбор и назначение замены, каскадное удаление и сохранение флагов с оставшимися ссылками. Временные записи откатили. Перед включением нужно проверить права роли на DELETE для досок, списков и флагов, а также на UPDATE для блокировок и назначения доски по умолчанию.

Создание и редактирование списков перенесены за выключенным по умолчанию `WORKSPACE_BRIDGE_SAVE_LIST`. Laravel проверяет прежний контракт, включая дату. .NET проверяет доступ к доске и флагу, назначает позицию в общей сетке и сохраняет список и новый флаг одной транзакцией. Проверка SQL на изолированной базе охватила права, позицию относительно заметок, разницу между пропущенной датой и `null` и откат при дубликате.

Закрепление списков и заметок, перестановка списков и смешанной сетки перенесены за выключенным по умолчанию `WORKSPACE_BRIDGE_CARD_LAYOUT`. Блокировка строки доски сериализует изменения раскладки. На `todo_inn_aspnet_test` в шести сценариях совпали HTTP-статусы, ответы и состояние БД у Laravel-контроллера и подписанного маршрута .NET. Проверены первый перенос списка, смешанный порядок, закрепление заметки, отказ для закреплённой карточки и другой доски, а также закрепление участником организации. Тестовые записи удалены, браузерный прогон предстоит.

Создание и редактирование заметок перенесены за выключенным по умолчанию `WORKSPACE_BRIDGE_SAVE_NOTE`. .NET сохраняет порядок общей сетки и флаги, проверяет доступ к доске и корректирует позицию изображения по длине текста в UTF-16. Редактирование сохраняет исходные байты и MIME изображения. Подписанный HTTP-маршрут проверен на `todo_inn_aspnet_test`, временные записи очищены.

Чтение, загрузка и удаление изображения перенесены за выключенным по умолчанию `WORKSPACE_BRIDGE_NOTE_IMAGE`. Laravel принимает прежние методы и multipart-форму по `/api/notes/{noteId}/image`, проверяет сессию и CSRF и передаёт запрос через подписанный мост. .NET проверяет доступ, тип и размер файла, ограничивает позицию длиной текста в UTF-16 и хранит вложение в текущем `BYTEA`. Запись блокирует доску, затем заметку. Подписанный маршрут проверен на `todo_inn_aspnet_test`, включая файл ровно 1 МиБ, шесть форматов по сигнатурам, побайтовое чтение, заголовки, отказ для чужой заметки и очистку вложения. Временные записи удалены. Браузерный прогон публичного маршрута предстоит.

Запись приглашений в организацию перенесена за выключенным по умолчанию `WORKSPACE_BRIDGE_INVITE_MEMBER`. Laravel сохраняет разрешение логина в e-mail по прежним правилам и доставку письма. .NET повторно проверяет принятую роль owner и записывает приглашение с хешем токена на семь дней. Публичный JSON сохраняет поля `invited` и `email_sent`. Проверка SQL на изолированной базе подтвердила отказ для manager, поля приглашения и конфликт адресов без учёта регистра. Тестовые записи и временное разрешение роли откатили. Для включения .NET-роли нужны SELECT и INSERT в столбцы `corporate_account_id`, `email`, `role`, `invitation_token_hash` и `invitation_expires_at` таблицы `corporate_account_members`. Принятие приглашения остаётся частью Laravel auth до переноса авторизации.

## Сквозная проверка и следующий шаг

Через публичный Laravel API на `todo_inn_aspnet_test` прошёл сквозной прогон с входом по существующему bcrypt-хешу, cookie-сессией и CSRF. Проверены чтение и поиск, запрет доступа к чужой доске, создание и редактирование досок, списков, заметок и задач, флаги, закрепление и перестановка карточек, multipart-загрузка с возвратом тех же байтов, удаление и ответ при недоступности .NET. Прогон использовал временные процессы и тестовые записи, которые затем удалены. Флаг записи приглашений в этом прогоне был выключен из-за отсутствия INSERT у тестовой роли. Доставка письма и браузерная проверка остаются отдельными проверками.

Вторая ступень началась с локального прототипа `/api/auth.php` в ASP.NET Core. Он доступен на loopback в окружении `Development` при `AuthPreview__Enabled=true`. Для временного запуска по HTTP на loopback нужно также задать `AuthPreview__AllowLoopbackHttp=true`. Прототип использует отдельные защищённые cookie, память процесса для сессий и временные ключи Data Protection. Реализованы все действия текущего маршрута авторизации, включая чтение сессии, вход, выход, регистрацию и восстановление пароля. Прототип ограничивает JSON и проверяет CSRF. Vite и публичный Laravel продолжают обслуживать текущий auth.

На временном .NET-хосте проверены гостевая сессия, ограничения 8192 и 1 500 000 байт, порядок ошибок, отказ при неверном CSRF, инвалидирование старой cookie и токена после выхода и недоступность прототипа в `Production`. Проверка не использовала PostgreSQL. До переключения нужны постоянное хранилище сессий, ключей и счётчиков, а также полный контракт авторизации.

В локальном прототипе перенесён `check_login_email`. Он возвращает выбор типов только для адреса, связанного с личным и корпоративным root-аккаунтами, как Laravel. На изолированной базе результаты сравнили с Laravel в десяти сценариях, включая формат адреса и совпадение без учёта регистра. Эти случаи не заменяют полную проверку совместимости валидатора.

Для проверки существующих паролей подключены согласованные `BCrypt.Net-Next` и `Isopoh.Cryptography.Argon2`. `LegacyPasswordVerifier` проверяет хеши bcrypt и Argon2id, созданные PHP, и не меняет их. Перед переключением сверить форматы и параметры хеширования на целевых базах по агрегатам без выгрузки самих хешей. Прототип ограничивает стоимость вычисления хеша, поэтому значения за пределами поддерживаемого диапазона нужно учесть до переноса.

Вход в прототипе поддерживает личные аккаунты, root-аккаунты организаций и старые корпоративные пользовательские записи. При совпадающем адресе выбор аккаунта предлагается после проверки пароля. Успешный вход отзывает прежний билет и меняет CSRF, выход отзывает билет даже при повторной отправке старой cookie. Чтение личной сессии сверяет `password_version` с PostgreSQL. На изолированной базе проверены оба формата паролей, режимы входа, неизменность хешей и отзыв сессий. Тестовые записи удалены. Билеты хранятся в памяти одного процесса и исчезают при его перезапуске.

Для реализованных auth-операций подключены лимиты в памяти процесса. Общее ограничение составляет 60 запросов в минуту на IP. Вход ограничен 30 запросами в минуту на IP и 5 на пару логин–IP. Предварительная проверка e-mail ограничена 20 запросами в минуту на IP и 10 в час на адрес. Изменение cookie и регистра логина или подстановка заголовков IP не сбрасывают лимит. Проверка выполняется после конверта запроса и CSRF, до обращения к PostgreSQL или проверки пароля. По HTTP проверены пороги, заголовок `Retry-After` и доступность выхода после исчерпания лимита входа.

В том же локальном режиме доступен `GET /api/profile.php`. Он читает профиль только по личной .NET-сессии и текущей версии пароля. На изолированной базе ответ совпал с Laravel, включая PostgreSQL-метки времени и аватар в data URI. Проверены ответы для гостя, root-аккаунта и отозванной личной сессии.

Прототип `POST /api/profile.php` сохраняет описание, ссылки, тему и аватар. Сохраняются запреты на смену логина, почты и типа аккаунта. Смена пароля сверяет текущий хеш под блокировкой строки, использует Argon2id с текущими базовыми параметрами PHP и увеличивает `password_version`. В HTTP-прогоне подтверждены сохранение двух сессий при обычном редактировании, их отзыв после смены пароля, проверка нового хеша в PHP и повторный вход через .NET. Прогон использовал временные учётные данные и записи в изолированной базе. Публичный маршрут продолжает работать через Laravel.

Сквозной тест подтверждает лимиты в 60 чтений и 30 сохранений профиля и 5 проверок текущего пароля за минуту. При превышении API возвращает HTTP 429 с `Retry-After`. Тест проверяет истечение окна на временной PostgreSQL без ожидания в реальном времени.

Проверки авторизации покрывают неверные и отсутствующие параметры входа, одинаковые ответы для неизвестного пользователя и неверного пароля, вход со старым bcrypt-хешем без перезаписи, выбор корпоративной учётной записи и отзыв старых cookie и CSRF при выходе. Для восстановления пароля отдельный тестовый хост перехватывает запрос к почтовому провайдеру. Проверяются одинаковый ответ для известного и неизвестного адреса, сохранение хеша токена, истечение и однократность ссылки, сбой доставки и отзыв сессии после сброса. Письма остаются в локальном тестовом журнале.

Проверки регистрации покрывают привязку подтверждения к сессии, одноразовый код, предел неправильных попыток, обязательное согласие и наличие одного владельца. Корпоративный сценарий проверяет формирование писем, хранение хеша токена, однократное принятие при двух одновременных запросах, привязку владельца при последующей регистрации, создание доски и атомарность при сбое записи. В рабочем пространстве дополнительно проверяются права на отправку приглашений и повторное приглашение с другим регистром адреса.

Сценарий рабочего пространства проверяет изоляцию личной доски, права менеджера на общей доске, CSRF, лимит тела запроса и защиту последней личной доски. В прогон входят создание и изменение доски, сроки списков, откат флага при конфликте, метаданные и остановка повторения задачи, перенос и удаление задач, буквальный поиск, закрепление и порядок заметок. Проверяются побайтовая передача PNG, JPEG, GIF, WebP, HEIC и AVIF, предел в 1 МиБ, отказ для чужого вложения, позиции в UTF-16 и каскадное удаление.

В том же прогоне проверяются изоляция личных и корпоративных уведомлений, повторная отметка о прочтении, сохранение сессии и CSRF после перезапуска API и отзыв старой cookie при выходе. Миграции отказываются работать до принятия baseline, а изменение схемы блокирует запись журнала.

Проверки конкуренции покрывают 12 параллельных созданий задач в одном списке и два одновременных запуска генератора повторов. Отложенная ошибка PostgreSQL на фиксации переноса сохраняет исходные списки и порядок; ошибка генерации отменяет все записи текущей серии, после чего её можно обработать заново. Для повторов проверяются переход с 31 января на конец февраля и обратно на 31 марта, восстановление 29 февраля в високосном году, сохранение недельного дедлайна и продолжение после предела в 366 экземпляров за запуск.

В локальном `Development` при `AuthPreview__Enabled=true` задайте `AuthPreview__SessionKeyDirectory` абсолютным путём к существующему каталогу вне репозитория. Каталог хранит ключи Data Protection. Ограничьте доступ к нему учётной записью процесса. Сессии и маркеры билетов хранятся в PostgreSQL в зашифрованном виде, просроченные записи удаляет фоновая очистка. На двух процессах .NET проверены общий лимит входа при параллельных запросах, сохранение счётчиков после перезапуска, истечение окна, пауза между письмами восстановления, отдельные лимиты профиля и записи в workspace, очистка и повторный прогон сессий. ### Постоянное хранение подтверждений и восстановления

В постоянном режиме подтверждения e-mail, отметки подтверждения для регистрации и ссылки восстановления хранятся в существующей таблице `todo_inn_auth_sessions` с шифрованием Data Protection и прежними сроками действия. Ссылка восстановления погашается в транзакции смены пароля. При откате транзакции подтверждение или ссылка снова доступны для повтора. Просроченные записи удаляет общая фоновая очистка.

На двух временных процессах .NET проверены подтверждение и восстановление после перезапуска, общие попытки проверки кода, однократное использование кода, подтверждения и ссылки, откат регистрации и недействительность ссылки после сбоя доставки. ### Локальный стенд Caddy и HTTPS

В окружении `Production` публичные контракты включаются явным `PublicApi__Enabled=true`. Укажите DNS-имя сайта в `PublicApi__Host`, локальный порт в `PublicApi__Port` и абсолютный путь к отдельному существующему каталогу ключей в `PublicApi__SessionKeyDirectory`. Примените baseline и миграции до подключения репетиционной базы. У двух активных процессов одного выпуска должны совпадать база и каталог ключей. Для development preview используйте другой каталог.

Kestrel слушает IPv4 loopback. Публичные маршруты принимают запрос только от локального прокси с HTTPS и ожидаемым Host. Приложение доверяет одной паре `X-Forwarded-For` и `X-Forwarded-Proto` от `127.0.0.1`, а лимиты используют IP клиента из обработанного запроса. Caddy принимает клиентское TLS-соединение и формирует эти заголовки по нему. Не включайте автоматическую обработку forwarded-заголовков через `ASPNETCORE_FORWARDEDHEADERS_ENABLED`. Cookie сессии и авторизации используют префикс `__Host-`, `Secure`, `HttpOnly` и `SameSite=Lax`. Подписанный Laravel bridge скрыт при включённом публичном API. [Документация ASP.NET Core о доверенных прокси](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/proxy-load-balancer?view=aspnetcore-10.0).

Соберите API командой `dotnet publish -c Release backend/Workspace.Api`. Запустите `dotnet Workspace.Api.dll` из каталога публикации с `ASPNETCORE_ENVIRONMENT=Production` и переменными выше. Стенд использует собранный `dist/`. Для запуска Caddy из корня проекта укажите тот же порт Kestrel.

```sh
export TODO_INN_API_PORT=8002
export TODO_INN_DIST_DIR="$PWD/dist" TODO_INN_FAVICON_DIR="$PWD/public"
export XDG_DATA_HOME="$(mktemp -d)"
caddy run --config backend/Caddyfile.staging --adapter caddyfile
```

Caddy отдаёт приложение на `https://localhost:8443`. В конфиге отключена установка локального CA в системное хранилище. В другом терминале для проверки передайте `curl --cacert` файл `caddy/pki/authorities/local/root.crt` внутри выбранного `XDG_DATA_HOME`. Маршруты `/health` и `/ready` проверяются напрямую на loopback Kestrel.

На свежей восстановленной копии PostgreSQL 18 через Caddy 2.11.9 прошли выдача страниц, ассетов и favicon, отказ при неверном CSRF, закрытая регистрация, вход со старым bcrypt-хешем, чтение профиля, поиск и загрузка PNG. После перезапуска Kestrel сохранились сессия и CSRF, вложение прочитано побайтно, выход отозвал сохранённую cookie. Проверены атрибуты cookie, отказ при неверном Host и прямом HTTP, отсутствие внутренних маршрутов на HTTPS-сайте, обработка IP клиента и защита от подмены forwarded-заголовков. `/ready` вернул 503 до миграций и 200 после них. Локальный development preview продолжил отвечать.

### Репетиция запуска под systemd

Шаблоны в [backend/systemd](../backend/systemd) рассчитаны на Linux. API и задача работают от системной учётной записи `todo-inn`. Для VPS x86-64 соберите самодостаточный релиз через `dotnet publish -c Release -r linux-x64 --self-contained true backend/Workspace.Api`. Разместите `api/`, `dist/` и `public/favicon.svg` под общим каталогом релиза и укажите на него `/opt/todo-inn/current`. Проверьте права чтения артефактов от имени сервиса. Ключи Data Protection создаются в `/var/lib/todo-inn/keys` вне каталога релиза и сохраняются между перезапусками и заменами сборки.

Подготовьте `/etc/todo-inn/aspnet.env` с правами `0600` и владельцем `root`. Укажите `ConnectionStrings__Workspace` для восстановленной тестовой базы, DNS-имя Caddy в `PublicApi__Host` и `Registration__Enabled=false`. Для проверки писем используйте тестовый транспорт или тестового получателя. Параметры режима, порта и каталога ключей заданы в unit API. Схема должна быть принята до запуска сервисов.

```sh
systemd-analyze verify backend/systemd/todo-inn-api.service backend/systemd/todo-inn-repeat.service backend/systemd/todo-inn-repeat.timer
systemd-analyze calendar '*-*-* 00:05:00 UTC'
```

1. Установите три unit-файла на стенде, выполните `systemctl daemon-reload` и запустите только `todo-inn-api.service`. Убедитесь, что `curl --fail http://127.0.0.1:8002/ready` возвращает 200.
2. Сохраните действующий маршрут Caddy и настройки запуска Laravel-задачи. Настройте на стенде тот же HTTPS-сайт с маршрутом `/api/*` на `127.0.0.1:8002`. Проверьте конфиг через `caddy validate` до перезагрузки Caddy. Проверьте вход, чтение и сохранение на той же базе.
3. Остановите запуск `tasks:repeat` в Laravel и дождитесь окончания текущего вызова. Включите `systemctl enable --now todo-inn-repeat.timer` и проверьте `systemctl list-timers todo-inn-repeat.timer`. Таймер работает в прежнее время 00:05 UTC. После простоя он может запустить задачу сразу. [Документация systemd.timer](https://www.freedesktop.org/software/systemd/man/257/systemd.timer.html).
4. Подготовьте одну тестовую серию с датой UTC сегодня. Запустите `systemctl start todo-inn-repeat.service` дважды последовательно. Сверьте, что первое выполнение добавило один экземпляр, а второе сохранило число экземпляров. Просмотрите `journalctl -u todo-inn-repeat.service`. Выполните этот сценарий только на восстановленной тестовой базе.
5. Для отката остановите и отключите `todo-inn-repeat.timer`, дождитесь завершения `todo-inn-repeat.service`, верните маршрут Laravel в Caddy и восстановите расписание Laravel. Проверьте вход и новые записи на той же базе, затем остановите .NET API. Восстанавливать дамп поверх изменений для этого отката не требуется.

На VPS Debian 13 проверен самодостаточный релиз Linux x64 на изолированном восстановлении production PostgreSQL 17. Baseline совпал, после миграций контрольные суммы строк и последовательностей остались прежними. Отдельный loopback Caddy подтвердил HTTPS, загрузку страниц и ответ API. В пользовательском systemd проверены запуск API, `/ready` и два вызова команды повторов. Публичный маршрут и действующее расписание Laravel в этой репетиции не переключались. Системные unit-файлы и браузерная проверка остаются этапами приёмки выпуска.

Кандидат [Caddyfile.production](../backend/Caddyfile.production) сохраняет два действующих перенаправления на `todo-inn.ru`, проксирует API на loopback и отдаёт файлы из того же релиза, что использует systemd. Шаблон применяется только при отдельном переключении production.

Production переключён на ASP.NET Core 23 ноября 2026 года. После переключения проверены HTTPS, страницы и ассеты, защищённая cookie .NET, закрытая регистрация, закрытый доступ к `/ready` снаружи и оба перенаправления доменов. API и таймер включены в systemd, расписание Laravel остановлено. Исходный PHP-релиз и резервная копия сохранены для отката.

## Правила данных и выпуска

- Не направлять тесты на development или production PostgreSQL.
- Не запускать `schema.sql`, `migrate:fresh`, `migrate:refresh`, `db:wipe` или автоматические EF migrations на пользовательской базе.
- Перед первым .NET baseline зафиксировать структуру, ограничения, sequence/identity и контрольные количества строк без выгрузки секретов.
- Перед каждым production cutover делать резервную копию и репетировать возврат маршрута и приложения.
- Не удалять предыдущую реализацию в том же шаге, который впервые переключает трафик.
- Не коммитить `.env*`, строки подключения, Data Protection keys, mail keys, cookies, runtime sessions или database dumps.

### Сохранение всех баз PostgreSQL

Зафиксировать назначение и подключение каждой базы до репетиции. Production остаётся на своей БД, `todo_inn_laravel_dev` остаётся локальной рабочей БД, исходная legacy-БД сохраняется отдельно, тестовые базы используются только для тестов. Не объединять базы, не подменять одну другой и не загружать локальный дамп в production.

Репетировать принятие схемы и откат на отдельной восстановленной копии. Сверять таблицы, ограничения, индексы, последовательности, число записей и выборочные данные до и после. Проверить ID, владение и корпоративные роли, хеши паролей, даты и порядок карточек, байты аватаров и изображений заметок. Для сравнений остановить запись на копии или использовать согласованный снимок. При любом необъяснённом расхождении остановить переключение.

На выпуске проверить актуальную резервную копию и возможность восстановления. Переключить API и планировщик согласованно, чтобы каждое задание выполнял один бэкенд. Для отката вернуть маршрут и планировщик Laravel на ту же production-БД и предварительно проверить, что Laravel может читать записи, созданные .NET. Восстановление дампа поверх базы после начала записи требует отдельного решения о сохранении новых данных.

### Приёмка пользовательских сценариев

Сравнить ответы обоих бэкендов на одинаковых тестовых данных. Проверить методы и статусы, поля JSON, `null`, пустые коллекции, даты, сортировку, заголовки и ошибки. Прогнать существующий интерфейс в браузере на настольном и мобильном размере. Проверить вход со старым паролем, восстановление пароля, отзыв сессий, сохранение профиля, роли, поиск, порядок карточек и задач после перезагрузки, повторения и изображения. Проверки почты выполняются с тестовым получателем или локальной заглушкой. Перед выпуском подтвердить работу старых закладок и существующей сборки фронтенда.
