# To Do Inn!

Учебное веб-приложение для управления задачами с интерфейсом на React, PHP JSON API и PostgreSQL.

## Технологический стек

| Область | Технологии |
| --- | --- |
| Разметка и стили | HTML5, SCSS (Sass) |
| Интерфейс | React 19, JSX, Fetch API |
| Frontend-сборка | Vite 6 |
| Обработка стилей | Gulp 5, Dart Sass |
| Локальная frontend-среда | Node.js 20.19+, npm |
| Backend | PHP 8.5, Laravel 13, Eloquent / Query Builder, JSON HTTP API |
| PHP-зависимости | Composer 2 |
| Backend-тесты | PHPUnit 12, отдельная PostgreSQL БД |
| База данных | PostgreSQL |
| Production-сервер | Debian 13, Caddy, PHP-FPM, HTTPS |

Production-сборка frontend создаётся локально в `dist/`. Node.js, npm, Vite и Gulp на production-сервере не требуются. PHP обслуживает API, PostgreSQL — хранение данных.

## Локальный запуск

1. Установите PHP 8.5 с `pdo_pgsql`, `mbstring`, `fileinfo`, Composer 2, PostgreSQL и Node.js 20.19+.
2. Установите PHP-зависимости: `composer install` (или `php composer.phar install`).
3. Настройте **`.env.laravel`**, отдельную локальную БД `todo_inn_laravel_dev` и схему по разделу ниже. В текущей рабочей копии они уже подготовлены. Не перезаписывайте `.env`, `.env.laravel` и существующие базы. `database/schema.sql` — исторический data-changing скрипт, он не используется для запуска Laravel.
4. Установите frontend-зависимости и соберите приложение:

   ```sh
   npm ci
   npm run build
   ```

5. Запустите Laravel API и Vite в двух терминалах:

   ```sh
   npm run dev:api
   ```

   ```sh
   npm run dev
   ```

    Откройте <http://localhost:5173>. Vite обслуживает исходники из `frontend/` и проксирует `/api` и `/favicon.svg` на Laravel `127.0.0.1:8001`. `dev:api` запускает `php artisan serve --env=laravel --no-reload --host=127.0.0.1 --port=8001`; флаг `--no-reload` сохраняет нужное окружение дочернего сервера.

   **Не используйте `php -S 127.0.0.1:8000 -t public` для основного приложения:** эта старая команда напрямую запускает legacy PHP и другую сессию. Не запускайте Laravel без `--env=laravel`, пока исходный `.env` сохранён для legacy.

   В этой рабочей копии `/usr/local/bin/node` — старый Node 20.17, а `/opt/homebrew/bin/node` — уже установленный Node 26. Для совместимой среды можно использовать `PATH="/opt/homebrew/bin:$PATH" npm run dev` (также для `build`, `test:frontend`, `dev:styles`), без переустановки Node.

Для разработки SCSS используйте `npm run dev:styles` в третьем терминале. Gulp пишет скомпилированный CSS в `frontend/css/style.css`; `npm run build` затем собирает HTML/React/CSS в `dist/`. Каталог `public/` — PHP web-root с сохранёнными legacy API и статикой, сборка его не перезаписывает. Размещение содержимого `dist/` рядом с `public/index.php` требует отдельного ручного шага при production-выпуске. Границы каталогов описаны в [architecture.md](architecture.md).

## Авторизация

Регистрация и вход доступны через Laravel JSON API `/api/auth.php`, настройки профиля — через `/api/profile.php`. URL сохранились, но контроллеры находятся в `app/Http/Controllers/`, а не в standalone `public/api/*.php`. Логин можно менять раз в 24 часа, пароль — после проверки текущего, а аватар JPEG/PNG/WebP размером до 1 МБ хранится в PostgreSQL. Основная и дополнительная почта проверяются на формат и уникальность, но пока не подтверждаются письмом. Пароли хранятся только как хеши; изменения защищены CSRF-токеном.

Схему рабочего пространства создают Laravel-миграции (или принимают через baseline для существующей БД). У каждого нового аккаунта автоматически есть доска «👋 Hello World!». Доски, списки, флаги и задачи сохраняются в PostgreSQL; тип доски и тип аккаунта пока не управляют доступом или совместной работой.

Восстановление пароля пока не реализовано: отправка e-mail и подтверждение владения адресом требуют настройки почтового сервиса. Типы командных и корпоративных аккаунтов пока сохраняются как выбор пользователя, но не включают совместный доступ.

Перед публичным развёртыванием необходимо отдельно настроить HTTPS, проверить ограничения входа/регистрации и общего трафика, резервное копирование и конфигурацию production-сервера. Laravel-лимиты не распространяются на прямой запуск оставленных legacy PHP-файлов.

## Переход на Laravel

**Локальное приложение переключено на Laravel.** React/Vite использует авторизацию, профиль и workspace Laravel на порту 8001. Сохранены URL страниц и JSON-контракты. При первом переходе войдите заново: native PHP-сессии не переносятся. В `frontend/js/api.js` параллельные начальные чтения сессии объединены в один запрос, чтобы cookie и CSRF принадлежали одной сессии; завершённые ответы не кешируются.

**Выбрана отдельная `todo_inn_laravel_dev`, а не исходная legacy-БД.** Более поздние изменения из legacy автоматически не копировались. Исходная БД, `.env` и standalone `public/api/*.php` сохранены. Это локальный переход, **не production-деплой**.

### Этап 1 — основа и существующая БД

Добавлены Laravel 13, Eloquent-модели пяти таблиц, начальная миграция, проверка существующей схемы и PHPUnit-тесты.

### Структура

- `frontend/` — исходные HTML-страницы, React (`frontend/js/`) и SCSS (`frontend/scss/`); генерируемый `frontend/css/` игнорируется Git. `vite.config.mjs` сохраняет прежние URL страниц.
- `public/` — PHP web-root с `index.php`, `favicon.svg`, сохранёнными `api/*.php` и legacy `css/style.css`; Gulp не меняет эти файлы.
- Подробная схема запросов, сборки и окружений — в [architecture.md](architecture.md).
- `app/Models/` — `User`, `Board`, `TaskList`, `UserFlag`, `Task`, связи и типы полей существующей БД.
- `app/Console/Commands/BaselineLegacyDatabase.php` — безопасное принятие legacy-схемы.
- `bootstrap/`, `config/`, `routes/`, `artisan`, `public/index.php` — основа Laravel.
- `app/Http/Controllers/AuthController.php` — совместимый Laravel API регистрации, входа, выхода и чтения сессии.
- `app/Http/Controllers/ProfileController.php` — чтение/сохранение своего профиля, смена логина/пароля и работа с аватаром.
- `app/Http/Middleware/` — проверка JSON/размера запроса и обязательного CSRF-токена.
- `server.php` — dev-router локального Laravel API, без прямого запуска legacy PHP-файлов.
- `database/migrations/` — новые версии схемы; начальная миграция создаёт только пустые таблицы, не переносит данные из старого SQL.
- `database/legacy-baseline.json` — неизменяемый эталон типов, nullable/default/identity, ограничений и индексов начальной схемы, без пользовательских данных.
- `tests/` — проверки Laravel, совместимости моделей и принятия БД без потери данных.
- `storage/`, `bootstrap/cache/`, `vendor/` — локальные/генерируемые файлы, не коммитятся.

### Раздельные окружения

| Назначение | Файл | База данных |
| --- | --- | --- |
| Основное локальное приложение Laravel | `.env.laravel`, переменные `DB_*` | `todo_inn_laravel_dev` — отдельная выбранная БД |
| Сохранённый legacy-вариант для отката | `.env`, переменные `PG_*` | Исходная legacy-БД, без автоматической синхронизации |

Laravel намеренно не подставляет `PG_*` вместо `DB_*`: ошибка в настройке не должна незаметно направить миграции в работающую БД. Файлы окружения с секретами игнорируются Git. Не перезаписывайте уже настроенные файлы.

### Установка и проверка основы

Нужны PHP 8.5 с `pdo_pgsql`, `mbstring`, `fileinfo` и Composer 2:

```sh
composer install
```

Если используется локальный portable Composer, вместо `composer` выполняйте `php composer.phar`. `composer.phar` не входит в Git; при новом клонировании установите Composer с [официального сайта](https://getcomposer.org/download/). Composer-скрипты не создают БД и не запускают миграции.

Для новой локальной настройки скопируйте `.env.example` в `.env.laravel` **без перезаписи существующего файла**, затем укажите `DB_*` для отдельной БД. Один раз создайте ключ этого окружения:

```sh
php artisan key:generate --env=laravel
```

Ключ нельзя перегенерировать при каждом запуске или деплое. Production впоследствии получит собственный ключ.

Для локальной отправки простого текстового письма укажите `MAIL_MAILER=resend`, `RESEND_API_KEY`, `MAIL_FROM_ADDRESS` и `MAIL_FROM_NAME` в `.env.laravel` (это отдельное окружение от legacy `.env`). Проверить настройку можно безопасной командой с указанным адресом-получателем:

```sh
php artisan mail:test you@example.com --env=laravel
```

Команда отправляет только тестовый текст и не подтверждает e-mail пользователя.

Через локального администратора PostgreSQL создайте `todo_inn_laravel_dev` и `todo_inn_laravel_test`, назначив владельцем пользователя приложения. В текущей рабочей копии эти БД и игнорируемые файлы окружения уже подготовлены; не создавайте их заново и не затирайте данные.

**Если dev-БД пустая:**

```sh
php artisan migrate --env=laravel
```

**Если dev-БД — копия существующей legacy-БД:**

1. Сначала сделайте дамп и проверьте восстановление в отдельную локальную БД. Не используйте production-секреты или исходную БД как цель восстановления.
2. Выполните проверку, не меняющую таблицы или журнал миграций:

   ```sh
   php artisan legacy:baseline --env=laravel
   ```

3. Только после успешной проверки запишите начальную версию схемы как уже существующую:

   ```sh
   php artisan legacy:baseline --env=laravel --apply
   php artisan migrate --env=laravel
   ```

`--apply` создаёт/заполняет только журнал `migrations`: не пересоздаёт таблицы, не меняет строки, ID, хеши паролей, аватары или sequence. При расхождении схемы операция останавливается. Эквивалентные формы PostgreSQL TEXT-массивов и дополнительные неуникальные индексы допустимы; новые ограничения уникальности требуют проверки. В production дополнительно требуется явный `--force`, но на этом этапе production-перенос не выполняется.

Начальную миграцию и JSON-эталон после принятия не редактируем; дальнейшие изменения оформляются новыми миграциями. Автоматический `down()` начальной миграции запрещён, чтобы откат не удалил принятые legacy-таблицы. Не применяйте к пользовательским данным `migrate:fresh`, `migrate:refresh` или `db:wipe`.

Прямой эквивалент `npm run dev:api`:

```sh
php artisan serve --env=laravel --no-reload --host=127.0.0.1 --port=8001
```

Флаг `--no-reload` нужен, чтобы дочерний PHP-сервер получил уже загруженные настройки отдельного `.env.laravel`. После изменения этого файла сервер перезапускается вручную.

Откройте <http://127.0.0.1:8001/up> для health check или <http://127.0.0.1:8001/api/auth.php> для JSON сессии Laravel. `server.php` направляет API в Laravel, даже если в `public/api/` ещё лежит файл с тем же именем. `/api/profile.php` и `/api/workspace.php` доступны с Laravel-сессией (без входа — JSON 401), а не запускают старый backend.

Основное локальное приложение работает на портах 8001/5173 с `.env.laravel` и Laravel-сессиями. Vite proxy уже переключён на 8001. Bare legacy-сервер на 8000 не нужен для этого режима.

### Этап 2 — авторизация в Laravel-preview

Совместимые операции по прежнему URL `/api/auth.php`:

- `GET` — CSRF-токен, публичный `user` личной сессии (или `null`) и `corporate_account` root-сессии (или `null`). Root- и личная сессии взаимоисключающие.
- `POST` с `action=send_verification_code` и `email` отправляет шестизначный код на адрес через Resend. Код хранится в общем файловом cache только как HMAC-хеш в течение 10 минут. Повторная отправка разрешена раз в минуту, также действуют лимиты 10 писем в час на адрес и 20 в час с одного IP. `POST` с `action=verify_email_code`, `email` и `code` проверяет код; действует лимит 5 попыток на код. Подтверждённый адрес привязан к сессии, регистрация без подтверждения отклоняется.
- Только при `APP_ENV=local` отправка письма отключена: для локальной регистрации используется временный код `285868`, который показывается в интерфейсе. В тестовом и production-окружениях этот код не принимается; там используются случайные коды и отправка писем.
- `POST` с `action=register` — поля `email`, `username`, `password`, `confirm_password`, `account_type` и поля выбранного типа аккаунта. После имени/фамилии личного аккаунта либо списка участников организации открывается финальный экран необязательных настроек: аватар JPEG/PNG/WebP до 1 МиБ, описание, дополнительная почта, GitHub, Telegram и тема (`light`, `dark`, `system`). Для ссылок принимаются только профили `github.com` и `t.me`. Обязательное `personal_data_consent` блокирует регистрацию; `marketing_consent` необязателен и по умолчанию выключен. Тексты согласий пока являются черновиками и не подходят для публичного запуска без замены и юридической проверки. Настройки личного аккаунта сохраняются в `users`, настройки организации/root — в `corporate_accounts`. Логин сохраняется с обязательным префиксом `@`; общая длина — 4–24 символа, после `@` требуется латинская буква, далее допустимы латиница, цифры, дефис и подчёркивание. Личный аккаунт (`individual`) требует `first_name` и `last_name`; необязательное `middle_name` (отчество) и имена принимают кириллические/латинские буквы и тире. Корпоративная регистрация (`corporate`) создаёт отдельную организацию/root-аккаунт в `corporate_accounts`, а не пользователя в `users`; она требует `organization_type`, `organization_name` и `administrators` (1–5 строк). Ровно один `owner` задаётся отдельным приглашённым контактом; он не обязан совпадать с root-логином или root-e-mail. Организация и личный аккаунт могут иметь одинаковый e-mail, при этом логины остаются раздельными. Остальные роли — `admin`, `manager` или `support`. По каждому участнику отправляется одноразовая ссылка на 7 дней; `@логин` принимается только для уже зарегистрированного пользователя с e-mail. Личная регистрация после принятия приглашения связывает членство с пользователем и создаёт первую общую корпоративную доску для owner. Пароль: 8–128 символов, строчная и заглавная латинские буквы, цифра и спецсимвол; пробелы запрещены. Финальная кнопка создаёт аккаунт, сохраняет настройки и отправляет корпоративные приглашения; успешный ответ — `201`.
- `POST` с `action=accept_corporate_invitation` и `token` — принимает одноразовое приглашение. Ссылка подтверждает владение e-mail; если аккаунта ещё нет, роль привяжется после регистрации с тем же адресом.
- `POST` с `action=login` — вход личного пользователя либо root-аккаунта организации по логину и паролю; успешный ответ содержит соответственно `user` либо `corporate_account`. Неверные данные — одинаковая ошибка `401` для отсутствующего аккаунта и неправильного пароля.
- `POST` с `action=logout` — выход и очистка сессии; ответ `{ "success": true, "data": { "logged_out": true } }`.

POST принимает только JSON: до 1 500 000 байт для `register` (чтобы вместить аватар до 1 МиБ в base64) и до 8192 байт для остальных операций. Методы, тип данных, JSON и размер проверяются до CSRF; некорректные запросы возвращают `405`, `415`, `400`, `413`. Проверка полей — `422`, конфликт логина/e-mail — `409`.

Для POST клиент должен сохранить cookie из GET и передать полученный `csrf_token` в заголовке `X-CSRF-TOKEN`. Одного `Sec-Fetch-Site: same-origin`, токена в JSON или cookie недостаточно. Неверный/устаревший токен возвращает `403`. После входа/регистрации и выхода нужно снова получить токен через GET. Cookies Laravel и native PHP различаются; ID сессии и CSRF-токен меняются при входе и выходе. Токены и публичные данные не кешируются. CORS явно отключён: frontend использует same-origin Fetch через Vite proxy, сторонним сайтам доступ не выдаётся.

Новые Laravel-пароли хешируются **Argon2id**, чтобы весь прежний диапазон 6–128 ASCII-символов учитывался без усечения bcrypt после 72 байт. PHP на будущей целевой машине должен поддерживать `argon2id` в `password_algos()`. Старые bcrypt-хеши проверяются как раньше, без сброса пароля и без автоматической перезаписи при входе. Чтение сессии не раскрывает пароль, e-mail или байты аватара.

Лимиты Laravel-preview (считаются попытки, а не только успешные операции):

| Операция | Ограничение |
| --- | --- |
| Общий лимит auth | 60 в минуту на IP |
| Вход | 30 в минуту на IP и 5 в минуту на пару логин + IP |
| Регистрация | 5 в час и 20 в сутки на IP |

Превышение возвращает JSON `429` и заголовок `Retry-After`. Неподдерживаемые методы, неверный формат/размер и CSRF отсекаются до этих лимитов; для ограничения всего входящего трафика нужна отдельная серверная защита. Регистр логина, смена cookie или непроверенные `X-Forwarded-For` / `CF-Connecting-IP` не сбрасывают соответствующий лимит. Используется общий файловый кеш для одного сервера; не заменяйте его на `array` вне PHPUnit. Доверенные прокси перед production-переносом настраиваются отдельно, не через wildcard `*`. Лимиты не заменяют защиту от распределённых ботов и могут затрагивать пользователей с общим IP.

Эта защита **не распространяется на прямой запуск сохранённых legacy API**. Локальный Vite больше к ним не обращается. Production-выпуск остаётся отдельной процедурой. Dev-БД нельзя восстанавливать поверх production: переносятся код и проверенные миграции, а не локальные аккаунты.

### Этап 3 — профиль в Laravel-preview

`GET /api/profile.php` возвращает `data.profile`: `id`, `username`, `email`, `secondary_email`, `account_type`, `about`, `github_url`, `telegram_url`, `preferred_theme`, `username_changed_at`, `username_change_available_at`, `avatar`. Пароль, хеш и сырые байты не включаются. Timestamp-поля остаются строками PostgreSQL с часовым поясом (или `null`), аватар — data URI (или `null`).

`POST /api/profile.php` сохраняет прежние поля формы:

- Логин можно менять не чаще одного раза в 24 часа. Новые логины используют формат `@` + латинская буква + латиница/цифры/`-`/`_`; прежние логины без `@` остаются допустимы для совместимости. Сохранение остальных настроек без смены логина разрешено в период ограничения.
- Основная/дополнительная почта нормализуются в нижний регистр без краевых пробелов; пустые значения становятся `null`, одинаковые адреса в одном профиле запрещены. Уникальность сохраняют существующие индексы БД.
- `about` — до 1200 Unicode-символов; `github_url` принимает ссылку на профиль `https://github.com/<username>`, `telegram_url` — `https://t.me/<username>`; `preferred_theme` — `light`, `dark` или `system`. Существующие значения `account_type` сохраняются для совместимости; корпоративное членство и доступ определяются отдельными записями организации и участника, а не этим полем личного профиля.
- Смена пароля требует `current_password`, `new_password`, `confirm_password`; текущий пароль проверяется по свежему хешу под блокировкой строки. Новый пароль — Argon2id, 6–128 ASCII-символов с буквой/цифрой, без пробелов. При обычном сохранении старый хеш не меняется.
- Без поля `avatar` фото сохраняется. `avatar: null` удаляет фото и MIME. Строка JPEG/PNG/WebP data URI проверяется по фактическому MIME, размеру до 1 048 576 байт и измерениям до 2048×2048. Бинарные данные по-прежнему хранятся в PostgreSQL `BYTEA`, без файлового хранилища и новых зависимостей.

Выбирается только профиль пользователя Laravel-сессии: `id`, `user_id`, хеш/даты/сырые байты из тела или query-параметров не дают доступа к чужим данным и не сохраняются напрямую. Изменения профиля, пароля и фото выполняются одной транзакцией; конфликт (`409`) или ошибка не оставляет частичных изменений.

Сохраняется порядок проверок legacy: вход (`401`) → допустимый метод (`405`, `Allow: GET, POST`) → CSRF (`403`) → JSON/размер (`400`/`413`) → поля (`422`). Как и раньше, профиль читает JSON независимо от `Content-Type`; тело ограничено 1 500 000 байт. Ошибки текущего пароля — `403`, слишком ранняя смена логина — `429`. SQL, пути и внутренние сообщения не выдаются даже с `APP_DEBUG=true`.

Текущая сессия и CSRF-токен при сохранении профиля не сбрасываются — существующая React-форма может продолжать отправлять запросы без перезагрузки. Это не функция выхода с других устройств. В preview добавлены отдельные лимиты: 60 запросов/минуту на IP, 60 чтений и 30 сохранений/минуту на аккаунт; проверки текущего пароля — максимум 5 попыток/минуту на аккаунт независимо от IP. Превышение лимитов возвращает `429` с `Retry-After`. Новые миграции схемы не потребовались; legacy PHP-файл остаётся нетронутым.

### Этап 4 — workspace в Laravel-preview

`app/Http/Controllers/WorkspaceController.php` сохраняет контракт `/api/workspace.php`, используя Laravel Query Builder и PostgreSQL. Новые миграции добавляют реквизиты root-аккаунта и связь корпоративных досок с организацией; новых зависимостей не требуется.

- `GET` возвращает `board`, `boards`, `flags`, `lists`, `tasks` личных досок пользователя и корпоративных досок организаций, в которых он состоит. Доска корпоративной организации выбирается первой; корректный, но недоступный/отсутствующий `board_id` даёт `404`, некорректный ID при чтении оставляет выбор доски по умолчанию, как в legacy. Также возвращается `corporate_accounts` с ролью текущего участника.
- Непустой `search` ищет по названию/описанию списка или названию задачи по всем своим доскам, без учёта регистра. `%` и `_` — обычные символы. Ответ `data.results` содержит подходящие списки со всеми их задачами и флагами соответствующей доски. Лимит поиска — 120 Unicode-символов, управляющие символы запрещены.
- `POST` принимает `create_board`, `update_board`, `create_list`, `update_list`, `create_task`, `update_task`, `toggle_task`, `reorder_task`, `create_flag`, а также `invite_member`. Все принятые участники могут работать со списками, флагами и задачами корпоративных досок; owner единственный может создавать/удалять корпоративные доски и приглашать участников. `admin`, `manager`, `support` пока имеют одинаковые права повседневной работы. `create_list` оставляет описание пустым; `update_list` сохраняет описание. Перестановка разрешена только внутри того же списка, без переноса задач между списками.
- `DELETE ?board_id=...` удаляет свою доску, но не последнюю; для удаляемой доски по умолчанию выбирается замена. `DELETE ?list_id=...` удаляет свой список. Связанные задачи удаляет существующий каскад БД. Неиспользуемый флаг удаляется только после исчезновения последней ссылки; общие флаги сохраняются. При наличии обоих параметров приоритет у `board_id`.
- Транзакция и блокировка строки текущего пользователя сериализуют workspace-записи, защищая выбор последней доски, очистку флагов и порядок задач от конкурирующих запросов. Исключения откатывают всю операцию, включая уже созданные флаги. Блокировка задач дополнительно сохраняется при перестановке. Проверяется также владелец списка задачи, поскольку legacy FK `tasks.list_id` сам по себе не связывает владельцев.

`PrepareWorkspaceRequest` сохраняет порядок: вход (`401`) → метод (`405`, `Allow: GET, POST, DELETE`) → для POST тип `application/json` (`415`) → обязательный `X-CSRF-TOKEN` (`403`) → тело до 8192 байт/JSON (`413`/`400`). На DELETE CSRF обязателен, но JSON-тело не требуется. Метод HEAD не становится разрешённым GET. Действия и поля POST не берутся из query, параметры GET/DELETE — не из тела. `user_id` не позволяет менять владельца. Сессия и CSRF при workspace-действиях не сбрасываются.

Отдельное удаление задачи, новые фильтры и отдельный rate limiter workspace не добавлялись. Перед публичным переключением нужны сквозная проверка интерфейса и оценка ограничений трафика; текущий preview не является production-конфигурацией.

### Тесты

Для новой настройки создайте `.env.testing` по `.env.example` без перезаписи существующего файла. Укажите `APP_ENV=testing`, `DB_DATABASE=todo_inn_laravel_test` и локальные учётные данные PostgreSQL. Не копируйте в эту БД реальные пользовательские данные.

```sh
composer test
# Или без Composer:
php vendor/bin/phpunit
# Регрессионные frontend-тесты, встроенный node:test, без новых зависимостей:
npm run test:frontend
```

Тесты используют PostgreSQL, а не SQLite. До соединения/миграций проверяются окружение, локальный адрес и точное имя тестовой БД; запуск с кешированной конфигурацией запрещён. Пустая тестовая БД инициализируется обычной миграцией, без удаления таблиц; записи и изменения схемы каждого теста откатываются транзакцией. Значения тестовых sequence могут увеличиваться.

Проверяются health check, безопасные JSON-ошибки, совместимость старых хешей паролей и `BYTEA`, связи/каскады/порядок задач, блокировка несовместимой схемы и сохранность строк/sequence при baseline. Тесты auth проверяют регистрацию/вход/выход, откат неполной регистрации, cookie/CSRF/смену сессии, JSON-контракт, пароль длиной 128 символов, запрет CORS и лимиты запросов. Тесты профиля проверяют владельца данных, 24-часовое окно логина, пароли, все три формата аватара и граничные размеры, удаление фото, неизменность сессии/CSRF и полный откат при ошибке. `WorkspaceTest` проверяет контракт досок/списков/флагов/задач, поиск, сортировку, строгие типы и лимиты, чужие ID, каскады, сохранение общих флагов, запрет удаления последней доски и откат при искусственной ошибке после записей. CSRF в тестах не отключается; тестовые изображения не требуют GD или загрузок из сети. `PreviewRouterTest` дополнительно поднимает временный loopback PHP-сервер, проверяет реальные cookies/CSRF, `401` для профиля/workspace без входа и JSON 404 для несуществующих API-путей, затем останавливает его и удаляет только собственное временное хранилище. Уменьшенные затраты Argon2id задаются только в `phpunit.xml`; это не production-настройки.

### Локальное переключение и откат

Проверен реальный React-интерфейс в Chromium через Vite → Laravel на изолированной тестовой БД: регистрация, переход в workspace, доска/список/задача, переименование/выполнение задачи, поиск, сохранение профиля/логина/пароля, выход, вход с новым паролем, сохранность задач после перезагрузки и удаление доски. Браузерный инструмент устанавливался отдельно во временный каталог, без зависимостей в проекте. Автоматические frontend-тесты фиксируют обнаруженную гонку начальной cookie/CSRF-сессии.

Для осознанного **локального** отката остановите Laravel и перенастройте proxy **`/api` и `/favicon.svg`** в `vite.config.mjs` на `http://127.0.0.1:8000`. Запустите старый `php -S 127.0.0.1:8000 -t public` и перезапустите Vite. Через Vite страницы из `frontend/` доступны по прежним URL, legacy API работает с отдельной исходной БД и требует повторного входа. Если необходимо обслуживать HTML напрямую с порта 8000, сначала вручную разместите собранные страницы и assets из `dist/` в `public/`, **не удаляя** `public/index.php`, `public/api/`, `public/css/style.css` и `public/favicon.svg`. Это не автоматический откат и не синхронизация данных: новые записи Laravel в legacy-БД не появятся. Не восстанавливайте базы поверх друг друга; перенос данных требует отдельного плана.
